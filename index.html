사업비 지출 관리 서비스 구축

서비스
Gravity - 4대 과학기술원 창업리그 사업비 지출 관리
기간
2026.06 - 2026.07 · 약 6주
역할
프론트엔드 단독 - 아키텍처 설계부터 배포 파이프라인까지
기술
Next.js 16 (App Router · Turbopack) · React 19 · TypeScript · Turborepo · TanStack Query · Zustand · Tailwind CSS v4 · MSW · Vitest · Docker · GCP Cloud Run · GitHub Actions

개요

4대 과학기술원 창업리그 Gravity의 정부지원사업비 지출 관리(예산 현황, 지출 요청 승인과 정산) 서비스를 프론트엔드 단독으로 신규 구축했습니다. 사용자 웹과 운영자 어드민 두 개의 앱을 Turborepo 모노레포로 부트스트랩하고, 백엔드 API와 동시에 착수한 조건에서 첫 커밋부터 6주 만에 1.0.0 정식 릴리스에 도달한 작업입니다.

문제상황

정부지원사업비는 일반적인 기업 경비와 성격이 다릅니다. 예산 항목별로 집행 한도가 정해져 있고, 지출은 요청 → 승인 → 정산의 단계를 거치며 각 단계마다 증빙이 남아야 합니다. 즉 틀린 숫자를 보여주는 것이 기능 부재보다 나쁜 도메인이고, 상태 전이가 곧 제품의 본질인 서비스였습니다.

여기에 프로젝트 조건이 세 가지 제약을 더했습니다.

  • 참고할 코드가 없었습니다. 기존 서비스를 확장하는 작업이 아니었습니다. 별도 프로덕트의 첫 커밋이라 폴더 구조, 상태 관리 규칙, 인증 방식까지 전부 정해야 했습니다.
  • 프론트엔드는 한 명이었습니다. 리뷰어가 없고 잘못 잡은 구조를 중간에 되돌릴 여유도 없다는 뜻입니다.
  • 백엔드 API와 동시에 시작했습니다. API가 나올 때까지 기다렸다가 붙이는 순차 개발로는 6주 안에 불가능했습니다.

사용자 앱과 운영자 어드민을 모두 만들어야 한다는 조건도 있었습니다. 두 앱은 같은 예산과 지출 도메인을 다루지만 권한과 화면이 다릅니다. 코드를 어디에서 나누고 어디에서 합칠지가 첫 번째 결정이었습니다.

해결방안

구조 영역에서는 세 가지 대안을 비교했습니다.

  • 단일 앱 라우트 분기: 하나의 Next.js 앱에서 사용자와 어드민을 라우트로 나누는 방식입니다. 어드민 전용 코드가 사용자 번들에 섞이고, 권한 경계가 라우트 컨벤션에만 의존하게 되어 기각했습니다.
  • 저장소 완전 분리: 예산, 지출 타입과 API 클라이언트를 양쪽에서 따로 관리해야 하고, 스펙이 바뀔 때마다 두 곳을 수동 동기화해야 합니다.
  • 모노레포 + 공유 패키지: 앱은 분리하되 도메인 지식은 한 곳에 둡니다. 타입 하나를 고치면 두 앱 모두에서 컴파일 에러로 드러나므로, 리뷰어 없이 개발하는 조건에서 실수를 기계가 먼저 잡아줍니다.

세 안 모두 같은 화면을 만들 수는 있습니다. 스펙 변경이 조용히 새지 않는 구조를 가장 잘 보장하는 쪽은 세 번째 안이었습니다. 그래서 apps/web, apps/admin 두 앱과 api, ui, types 공유 패키지 3종으로 설계했습니다.

인증은 지출 승인 권한이 걸린 서비스라는 점에서 별도로 설계했습니다. 토큰 노출이 곧 결재 권한 탈취인 동시에, 예산 검토 화면에 오래 머무는 사용 특성상 세션이 끊겨 로그인 화면으로 튕기는 경험도 치명적이었습니다. Next.js 서버 라우트를 인증 프록시(BFF)로 두고 토큰은 httpOnly 쿠키에만 보관해 클라이언트 JavaScript가 토큰을 읽을 수 없게 했고, 만료가 감지되면 프록시 단에서 갱신한 뒤 원 요청을 재시도하도록 만들었습니다. 대시보드는 화면 하나가 여러 API를 동시에 부릅니다. 만료 시점에 갱신 요청이 동시다발로 나가지 않도록 갱신은 한 번만 수행하고 나머지 요청은 그 결과를 기다리게 했습니다.

일정 제약은 개발 순서를 바꿔 해결했습니다. API 스펙 합의 직후 MSW로 목 핸들러를 먼저 구현하고 화면은 목을 상대로 개발했습니다. 실제 서버가 준비되면 핸들러만 끄면 되므로 화면 코드는 건드리지 않습니다. 같은 목 핸들러를 Vitest에서 그대로 재사용할 수 있어 목을 만드는 비용이 테스트 인프라 비용을 겸했습니다.

배포는 환경변수 처리 방식을 바꿨습니다. Next.js는 기본적으로 빌드 시점에 환경변수를 코드에 굽습니다. 그대로 두면 개발, 스테이징, 운영마다 별도 이미지를 빌드해야 하고 스테이징에서 검증한 것과 운영에 뜬 것이 같은 빌드인지 보장할 수 없습니다. 환경 의존 값을 컨테이너 기동 시점에 주입하도록 구성해 하나의 이미지로 세 환경에 배포했습니다.

화면 영역에서는 다음을 만들었습니다.

  • 지출 요청 칸반 보드 - 요청, 승인, 정산이라는 도메인의 상태 전이를 화면 구조와 일치시켰습니다. 목록과 필터로 표현하면 사용자가 "지금 내가 처리해야 할 것"을 스스로 찾아야 하지만 칸반은 단계 자체가 화면이므로 처리 대상이 위치로 드러납니다.
  • 예산 현황 화면 - 항목별 배정액, 집행액, 잔액을 집계해 보여줍니다. 승인 대기 중인 금액을 어떻게 취급하느냐에 따라 잔액이 달라지므로 계산 규칙을 별도 모듈로 분리했습니다.
  • 인증, 권한, 예산 계산 로직의 단위 테스트 - 테스트를 전면에 깔 시간은 없었기에 틀리면 가장 비싼 세 곳에만 집중했습니다. 숫자가 틀리거나 권한이 새는 것은 화면이 덜 예쁜 것과 비용이 다릅니다.

결과

  • 첫 커밋부터 약 6주 만에 1.0.0 정식 릴리스에 도달했고, 프로젝트 내 최다 기여자로 전체 커밋의 60%를 담당했습니다.
  • 4대 과학기술원 140개 팀이 약 30억 원 규모의 사업비를 이 서비스로 관리하고 있으며, 릴리스 이후 1,000건 이상의 지출 요청이 처리됐습니다.
  • 목 우선 개발로 백엔드 API 완성을 기다리는 대기 구간을 없앴습니다. 프론트엔드 일정은 백엔드 일정에 종속되지 않았습니다.
  • 단일 이미지로 3개 환경에 배포할 수 있게 되어 환경별 빌드가 사라졌습니다. 검증한 아티팩트가 그대로 운영에 올라가는 것이 보장됩니다.
  • 사용자 웹과 어드민 두 앱, 그리고 이후 프로젝트에서도 재사용 가능한 공유 패키지 3종을 남겼습니다.

회고

6주라는 기간을 지킨 결정적인 이유는 목 우선 개발이었습니다. 백엔드 일정에 의존하는 구조였다면 릴리스 날짜를 장담할 수 없었을 것입니다. 테스트도 커버리지를 목표로 삼지 않고 금액과 권한처럼 실패 비용이 큰 영역에만 넣었는데 그 판단이 리소스 대비 효과가 좋았습니다.

E2E 테스트는 넣지 못했습니다. 단위 테스트는 계산과 권한을 지켜주지만 요청 → 승인 → 정산이라는 전체 흐름이 화면에서 끊기지 않는지는 보장하지 못합니다. 핵심 시나리오 한두 개만이라도 E2E로 잡아뒀다면 릴리스 직전의 확인 비용이 줄었을 것입니다. 공유 UI 패키지도 무엇이 공통인지 확정되기 전에 열었기 때문에 초기에는 한쪽에서만 쓰는 컴포넌트가 들어가기도 했습니다. 두 번째 사용처가 생긴 뒤 올린다는 규칙을 처음부터 명시했어야 했습니다.

연구자 커뮤니티 데이터 계층 규약화

서비스
뮤니(muni) - 연구자 커뮤니티 플랫폼
기간
2026.05 - 2026.07 · 약 2개월
역할
모노레포 아키텍처 · 데이터 계층 규약 · 인증 · 인프라 - 전체 커밋의 78%
기술
Next.js 16 · React 19 · TypeScript · Turborepo · TanStack Query · MSW · Vitest · Docker · Kubernetes · GitHub Actions

개요

게시글, 댓글, 좋아요, 프로필로 이루어진 연구자 커뮤니티 플랫폼을 구노 계정 연동을 포함해 신규 구축했습니다. 화면을 만드는 것과 별개로, 여러 사람이 같은 방식으로 서버 상태를 다루도록 데이터 계층의 사용 규약을 설계한 것이 이 프로젝트의 중심이었습니다. 약 2개월 만에 1.0.0-beta에 도달했고 전체 커밋의 78%를 담당했습니다.

문제상황

기능 목록만 보면 평범하지만 커뮤니티 서비스에는 다른 도메인에 없는 특성이 두 가지 있었습니다.

  • 상호작용의 빈도가 높고 단위가 작습니다. 좋아요 한 번, 댓글 한 줄마다 서버 왕복을 기다리게 하면 체감 품질이 곧바로 떨어집니다. 반대로 즉시 반영하면 실패했을 때 되돌리는 처리가 필요합니다.
  • 같은 데이터가 여러 화면에 동시에 존재합니다. 목록의 좋아요 수, 상세의 좋아요 수, 프로필의 활동 내역이 같은 사실을 가리킵니다. 한 곳에서 바뀌면 나머지가 따라가야 하는데, 무엇을 다시 불러올지를 개발자마다 다르게 판단하면 새로고침해야만 반영되는 화면이 생깁니다.

여기에 기존 구노 사용자를 그대로 들여와야 한다는 조건이 붙었습니다. 신규 커뮤니티에 회원가입 장벽을 세우는 대신 구노 계정으로 로그인하게 하는 OAuth 연동이 필요했습니다. 외부 시스템에 의존하는 플로우라 실환경 디버깅 비용이 가장 비싼 영역이기도 했습니다.

해결방안

TanStack Query를 쓰면서 가장 흔하게 무너지는 지점은 쿼리 키를 각자 문자열로 적는 것입니다. 키가 흩어지면 "이 뮤테이션이 무엇을 무효화해야 하는가"가 코드에 남지 않고 사람의 기억에 남습니다. 그래서 두 가지를 규약으로 고정했습니다.

  • queryKey factory: 키를 도메인별로 중앙화해 무효화 범위가 계층 구조로 표현되게 했습니다. "이 게시글만", "게시글 목록 전체", "이 사용자 관련 전부"를 팩토리 호출 하나로 지정할 수 있고, 오타 때문에 아무것도 무효화되지 않는 사고가 사라집니다. 새로 합류한 사람이 키를 새로 발명할 필요도 없어집니다.
  • 낙관적 업데이트 헬퍼: 이전 캐시 스냅샷 저장 → 즉시 반영 → 실패 시 복원 → 성공, 실패와 무관한 재검증이라는 정해진 절차를 헬퍼로 추출했습니다. 매번 손으로 쓰면 어느 하나가 빠지고, 빠진 자리는 조용히 잘못된 화면으로 남습니다. 사용자는 클릭 즉시 반영된 화면을 보고, 실패하면 원래 상태로 되돌아갑니다.

구노 계정 연동은 외부 시스템 왕복이 포함되어 실패 경로가 많고, 실환경에서 디버깅하기 가장 번거로운 종류의 기능입니다. 순서를 세 단계로 나눴습니다.

MSW 목으로 플로우 고정 → 단위 테스트로 분기 고정 → 실백엔드 연동

로그인, 신규 가입, 이미 연동된 계정, 실패와 취소까지 각 분기를 목으로 재현해 외부 서비스를 호출하지 않고도 화면 전이를 전부 확인할 수 있는 상태를 먼저 만들었습니다. 목이 있으니 그대로 테스트에 쓸 수 있었고 실연동 시점에 남는 문제는 대부분 리다이렉트 URI나 쿠키 도메인처럼 실제 환경 고유의 것으로 좁혀집니다. 로직 버그와 환경 문제가 섞이지 않는 것이 이 순서의 목적이었습니다.

배포는 Docker 멀티스테이지 빌드로 빌드 도구와 개발 의존성이 최종 이미지에 남지 않게 구성하고, GitHub Actions CI와 Kubernetes 배포 매니페스트를 직접 작성했습니다. 프론트엔드 코드와 그것이 실제로 뜨는 방식까지 함께 책임졌습니다.

마지막으로 같은 질문에 매번 답하는 대신 리팩토링 지침서를 포함한 반복 패턴 문서를 작성했습니다. 컴포넌트를 어느 시점에 쪼갤지, 서버 상태와 클라이언트 상태의 경계를 어디에 둘지처럼 사람마다 갈리는 판단을 글로 고정했습니다.

결과

  • 약 2개월 만에 1.0.0-beta에 도달했고, 전체 커밋의 78%를 담당했습니다.
  • queryKey factory와 낙관적 업데이트 헬퍼로 데이터 계층의 사용 방식이 통일됐습니다. 이제 캐시 무효화 판단은 개인의 기억에 기대지 않고 코드에 남습니다.
  • Docker 멀티스테이지 빌드, GitHub Actions CI, Kubernetes 배포 매니페스트를 자체 구축해 배포 경로를 팀 외부에 의존하지 않게 만들었습니다.
  • 리팩토링 지침서 등 반복 패턴 문서화로 신규 인원의 온보딩 학습 시간을 단축했습니다.

회고

관측 가능성 체계 구축

서비스

기간

기술

개요

인프라, 마이크로서비스, 프론트엔드 세 층에 흩어져 있던 상태 정보를 하나의 추적 체계로 연결했습니다. Datadog Infrastructure, APM, RUM을 각각 연동하는 데서 멈추지 않고 APM과 RUM을 trace_id로 묶었습니다. 사용자의 클릭에서 시작해 백엔드 내부 처리까지 하나의 타임라인으로 따라갈 수 있게 만든 작업입니다. 병목 원인 파악 시간을 3시간에서 20분으로 줄였습니다.

문제상황

장애 대응 시간이 길었던 이유는 고치는 데 오래 걸려서가 아니라 어디가 문제인지 찾는 데 오래 걸려서였습니다. 문제는 세 층에 각각 존재했습니다.

  • 인프라 층: GKE 클러스터의 노드와 Pod 리소스 사용량을 실시간으로 볼 수단이 없었습니다. 메모리 압박이나 재시작 같은 신호는 이미 사용자 영향이 발생한 뒤에야 알게 됩니다.
  • 서비스 층: 하나의 요청이 여러 마이크로서비스를 거치는데, 전체 응답이 느릴 때 어느 구간이 느린지 알 수 없었습니다. 결국 의심 가는 서비스의 로그를 하나씩 뒤지는 방식이 됩니다.
  • 프론트엔드 층: "안 돼요"라는 제보가 들어와도 어떤 브라우저에서 무슨 순서로 조작했을 때 발생했는지 알 수 없어 재현에만 대부분의 시간이 들어갔습니다. 재현하지 못하면 수정할 수도 없습니다.

세 층이 따로 놀았기 때문에 "사용자가 겪은 느린 화면"과 "특정 서비스의 느린 쿼리"를 연결할 방법도 없었습니다. 같은 사건인데 서로 다른 조각으로 남아 있었던 셈입니다.

해결방안

세 층을 각각 연동한 뒤 마지막에 하나로 꿰는 순서로 접근했습니다.

  • Infrastructure - GKE 클러스터, 노드, Pod 단위 리소스 모니터링을 붙이고 알림 체계를 구성했습니다. 목표는 사용자 영향이 생기기 전에 리소스 이상이 먼저 알려지는 상태였습니다. 대시보드를 들여다보는 일 자체에는 목적을 두지 않았습니다.
  • APM - 분산 트레이싱을 연동해 요청이 어떤 서비스들을 거쳤고 각 구간이 얼마나 걸렸는지 남게 했습니다. "느리다"가 "이 구간이 느리다"로 바뀌는 지점입니다.
  • RUM - 세션 리플레이, 에러 트래킹, Core Web Vitals를 수집했습니다. 특히 세션 리플레이는 재현 시도 자체를 없애줍니다. 재현하는 대신 일어난 일을 보면 됩니다.
  • APM과 RUM 연결 - 앞의 셋은 각각 유용하지만 따로 있으면 여전히 사람이 조각을 이어붙여야 합니다. 브라우저에서 발생한 요청과 백엔드 트레이스를 같은 식별자로 묶어 엔드 투 엔드 추적을 완성했습니다.

결과

  • API 성능 병목의 원인 파악 시간을 평균 3시간 → 20분으로 단축했습니다. (89% 단축)
  • 트레이싱으로 병목 구간을 특정한 뒤 Slow Query를 최적화해 특정 API 응답 시간을 2.3초 → 0.4초로 개선했습니다. (83% 단축)
  • 세션 리플레이를 활용해 프론트엔드 에러 원인 분석 시간을 3시간 이상 → 약 30분으로 줄였고, 장애 발생 시 MTTR을 2시간 이상 → 약 1시간으로 줄였습니다. (도입 전후 각 약 5개월, 에러 10건 이상 · 장애 1건 기준)
  • 인프라 리소스 이상 징후를 조기에 감지하게 되면서 장애가 난 뒤 대응하는 방식에서 장애 전에 손 쓰는 방식으로 대응 체계가 옮겨갔습니다. 도입 후 사용자 신고보다 알림이 먼저 울려 장애를 사전에 감지한 사례가 1건 있었습니다.

회고

APM과 RUM을 각각 켜는 것으로 끝냈다면 "두 개의 대시보드"가 늘었을 뿐입니다. trace_id로 묶는 마지막 한 걸음이 사람의 수작업을 없앴습니다. 2.3초가 0.4초가 된 것도 관측 도구가 저절로 만들어준 값이 아닙니다. 관측으로 병목을 특정한 뒤 실제로 고쳐서 나왔습니다. 도입에서 멈추지 않은 것이 이 작업의 가치입니다.

레거시 랜딩 페이지 렌더링 전략 재설계

서비스
구노 - 서비스 랜딩 페이지 (CRA → Next.js)
기간
2024.05 - 2024.10 · 약 6개월
역할
렌더링 전략 수립 · SEO 최적화 · 성능 개선
기술
Next.js (App Router · SSG/SSR) · TypeScript · Redux · next/image · Google Search Console

개요

CRA로 만들어져 클라이언트에서만 렌더링되던 랜딩 페이지를 Next.js App Router로 재설계했습니다. 페이지 성격에 따라 정적 생성과 서버 사이드 렌더링을 나누고 SEO 요소를 갖춰 Lighthouse Performance를 45점에서 92점으로, LCP를 4.2초에서 1.1초로 개선하고 오가닉 트래픽을 35% 늘린 작업입니다.

문제상황

랜딩 페이지는 제품을 처음 접하는 사람이 도착하는 곳이고 그 사람 대부분은 검색을 통해 옵니다. 그런데 이 페이지는 클라이언트에서 JavaScript가 실행된 뒤에야 내용이 생기는 구조였습니다. 두 종류의 방문자 모두에게 불리했습니다.

  • 검색 엔진: 크롤러가 처음 받는 HTML에는 실질적인 내용이 없습니다. 색인이 제대로 되지 않으면 그 뒤의 모든 유입이 막힙니다.
  • 사람: Lighthouse Performance 45점, LCP 4.2초. 주요 콘텐츠가 보이기까지 4초가 넘게 걸린다는 뜻이고 유입 단계에서 이탈이 발생하는 구간입니다.

즉 이 문제는 "페이지가 느리다"가 아니라 "유입 경로 자체가 막혀 있다"였습니다. 마케팅 비용을 늘려도 새는 구조였습니다.

해결방안

전부 SSR로 바꾸는 대신 페이지 성격에 따라 렌더링 전략을 나눴습니다. 콘텐츠가 자주 바뀌지 않는 페이지는 정적 생성(SSG)으로 미리 만들어두고 요청 시점 데이터가 필요한 페이지만 서버 사이드 렌더링(SSR)으로 처리했습니다. SSG로 처리 가능한 페이지를 SSR로 두면 매 요청마다 불필요한 서버 작업이 생기기 때문입니다.

그 위에 검색 엔진이 읽을 정보를 갖췄습니다. 메타 태그, Open Graph, Sitemap을 적용했습니다. Open Graph는 검색 순위와는 별개로 링크가 공유될 때의 표시 품질을 결정하므로 유입 경로 하나를 더 살립니다.

마지막으로 LCP를 직접 겨냥했습니다. 랜딩 페이지에서 LCP를 결정하는 것은 대개 첫 화면의 큰 이미지입니다. next/image로 포맷과 크기를 최적화하고 첫 화면 밖 이미지는 Lazy Loading으로 미뤄 초기 로딩 경로에서 제외했습니다.

결과

  • Lighthouse Performance 점수를 45점 → 92점으로 올렸습니다.
  • LCP를 4.2초 → 1.1초로 단축해 (74% 단축) Core Web Vitals 기준의 "좋음"(2.5초 이하) 구간에 들어갔습니다.
  • "연구노트", "전자연구노트" 등 핵심 키워드의 검색 노출 순위가 상승하면서 오가닉 트래픽이 35% 증가했습니다. (마이그레이션 전후 각 3개월 비교)
  • 기술 지표가 비즈니스 지표로 이어진 사례였습니다. 성능 개선 자체를 목표로 두지 않고 유입이라는 목적의 수단으로 놓은 것이 렌더링 전략을 선택할 때의 기준이 되었습니다.

회고

"Next.js로 옮긴다"는 과제를 "어떤 페이지를 언제 렌더링할지 정한다"로 바꿔 잡은 것이 성능 결과를 만들었다고 생각합니다. 마이그레이션 자체가 목적이었다면 전부 SSR로 옮기고 끝냈을 것입니다.

성능 판단의 근거를 Lighthouse 점수에 의존한 것은 아쉽습니다. Lighthouse는 실험실 측정값이라 실제 사용자 환경의 성능은 다를 수 있습니다. 실사용자 기반 Core Web Vitals를 함께 봤다면 개선 효과를 더 정확히 말할 수 있었습니다. 이 관점은 이후 Datadog RUM을 다루며 배웠습니다. 색인과 순위는 배포 직후가 아니라 몇 주에 걸쳐 반영되므로 Search Console 지표를 정기적으로 남기는 루틴도 함께 만들었어야 했습니다.
